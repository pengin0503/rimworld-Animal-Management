## 同一条件の比較
基準commit `f382c94e11303ccb350681706eb29215616b0abc` と修正後commitを同じセーブ/同一MOD順/同一RimWorld版/同一CPU・ゲーム速度・画質で比較。可能なら **各3回、ウォームアップ後の中央値・最大またはp95** を採用。オフライン純モデルのベンチマークをゲームTPSと混同しない。環境情報（入植者/動物/スタック/放牧地/天候/Mods数）を必ず添える。

## CIで回せる回帰行列
| ケース | 重要な期待値 |
|---|---|
| 2つの材料Def→同じ栄養Pool | 控除A+B・上限を超えず他消費者の不足悪化なし (#25) |
| 同一材料Def→複数Pool | 実消費可能な候補の最大影響を考慮、証明できないAutoは拒否 (#25) |
| Bill3回→1回→残2回→0回 | 正常進捗の所有継続と完了後の再利用可能性 (#21) |
| Bill手動変更・禁止・削除・ロード | 管理解除と二重生成なし、手動を上書きしない (#21) |
| 既存のHay/Kibbleがゼロ | 適正頭数と条件付き飼料案内が表示、Auto操作は無証明なら停止 (#19) |
| 非対象種が不足、対象種は充足 | 対象種の維持頭数を計算、非対象種の不足悪化なし (#22) |
| 生産モードOFF | 適正頭数の表示が独立、Bill新規作成なし (#24) |
| 放牧あり＋予測完全/不完全 | 保守的証明の有無に応じたAuto判定 (#20) |
| 繰り返し抑止理由発生 | 履歴20件の上限、毎Tickスパムなし (#26) |

## 性能比較項目 (#23)
- Pure model: 消費者10/100/400・飼料Pool 1/20/200・7/15/30日の `NutritionForecast.Run` と `FeedActionPlanner.Plan` の処理msとGC割当（測定APIの可用性を明記）。
- Map scan: 飼料スタック100/1000/12000、動物10/100/400、放牧セル0/30000の `FeedForecast.Recalculate` 計測。12k/30kなど走査上限到達時のPartialも比較。
- Game: 同一セーブで基準/修正版・Auto off/onを比較、平均/1% low TPS（計測手段がある場合）と計算時間、GC、エラー数を記録。再現できないTPS数値は記載しない。

## 通常ゲームで必要な手動検証（既存 #6 と連動）
- Kibble材料を別途消費する入植者と家畜がいる状態で、製造1回、材料消費、Bill回数減少、翌日の再補充を確認。
- 飼料ゼロ、冬季、複数食性、セーブ/ロード、MOD途中導入/削除、MOD設定Off/Confirm/Auto変更、翻訳の可読性。
- 270+ MOD構成は実施できる場合のみ。実行できなかった場合は「未検証」と記録。
