# Animal Management：行動につながる飼料管理（設計、未実装）
> Status: design only, 2026-11-02

## 意図・決定
単なる栄養予測を「必要な補充量・生産計画・維持できる家畜数」という行動可能な助言へ変換する。既存の予測と警報を再利用する。既存の飼料予測・放牧地計算を置き換えない。古いGrazing Infoと一部機能が重複しても構わない。

**基準:** RimWorld 1.7.4985 rev1269（R2 `rimworld-17/Game-Linux/`、既存解析 `research/vanilla-1.7.4985/`）。実作業時には最新API差分を確認する。現行v1.0.1は利用者による実プレイ確認済み・正常との申告を受けている。これは新機能の検証結果ではない。

**4機能共通の操作モード:** Off / Confirm（初期設定）/ Auto。Confirmは内容・対象・副作用を表示して明示承認後に限り変更する。Autoは機能別許可・対象別許可・範囲・上限に従い変更する。拒否条件、無効なスナップショット、状態変化、競合検出時は提案のみまたは停止。自動による不可逆行為は通常のAuto許可に含めない。

**共通安全性:** 手動で禁止・一時停止された対象を自動解除しない。プレイヤーの後からの変更を優先し、同じ操作を繰り返さない。計算根拠と変更前後を表示し、セーブへの履歴保存・クールダウン・レート上限・マップ別管理を設ける。対象削除・改名・移動・マップ切替・ロード・MOD削除時に破損しない。外部MODが管理する設定は原則読取専用、対応保証のない場合は変更停止。UI/設定は日英同等。

## 対象A1：不足解決と冬越し備蓄目標
- 予測日数を7/15/30日から選択。冬越し目標は推計可能な期間内で算出し、30日を超える季節・天候の確実性を装わない。
- `ForecastSnapshot` と `NutritionForecast.Run` による共有飼料配分を用い、食性・人間との競合・腐敗・立ち草・季節成長を維持する。単純な不足栄養合算や単一の栄養/個換算で断定しない。
- 「不足する栄養量」「指定した干し草/キブル等で埋める場合の必要個数」「現在の生産能力での達成見込み」「計算条件」を提示。
- 異なる飼料を候補にする場合は、`ThingDef` と `RecipeDef` の実データから食性・製品個数・材料・調理/栽培の制約を検証。任意のMOD食品を根拠なく換算しない。
- 部分スキャン・時間切れ・不明な到達性・将来の天候変動では「暫定/不確実」と表示し、自動操作の入力にしない。
- 現在の栄養予測を再実行するwhat-if計算によって、候補飼料の追加量を探索。追加した飼料が実際に利用可能かを検証できなければ追加量を確定しない。

## 対象A3：生産半自動化と適正頭数
- 生産提案は、既存の加工設備・レシピ・材料・保管条件を確認して提示。キブル等の製造指示が対応可能な場合、Confirmではプレビュー後に作成・調整。干し草栽培は「必要面積/栽培日数/既存ゾーンの必要量」を先に提示し、根拠のない新規栽培区画の自動生成はしない。
- Autoは許可された飼料の製造指示だけを管理し、MODが作った指示の識別子を保存。手動の指示・停止・レシピ・優先度・目標数は無断変更しない。重複指示を作らず、最終変更と余裕量を使って増減の振動を防ぐ。
- 「今の頭数」「放牧地の生産可能量」「共通備蓄」「動物種別の必要栄養」を使い、維持可能な頭数と超過分の候補を複数シナリオとして提示。共通の餌を二重計上しない。繁殖・妊娠・成長段階などの未知を幅で表示。
- バニラの自動屠殺設定への変更は提案またはConfirmが基本。Autoでも別途「自動屠殺設定の調整を許可」を明示ONしない限り行わない。絆・妊娠中の個体を保護し、直接の屠殺指示は出さない。設定変更が結果として不可逆な屠殺につながることを明示する。
- サイクルは例として1日単位、目標との差が閾値を超える場合のみ。設定変更・餌の補充・生産指示の完了後は予測を更新してから再判断する。

## UIと保存
- 既存 `Window_FeedForecast` の冒頭に「解決策」「生産計画」「適正頭数」へのタブ/折畳みを追加。予測の不確実性・根拠と施策の変更プレビューを見られる。
- `AnimalSettings` に機能別モード、目標日数、安全余裕、許可する飼料/設備、更新間隔、生産指示上限、不可逆操作の別許可を保存。既存セーブはConfirmと全自動操作OFFに移行。
- セーブ固有の所有するBill ID・変更履歴・クールダウンはMapComponentで保存。プレイヤーが指示を編集したら自動管理対象から外す。
- 異なるMODの動物・飼料・加工レシピ・放牧を安全に扱い、APIに存在しない植物の成長を想像で埋めない。

## 競合・失敗条件
- 他MODが同じ製造指示や飼育条件を制御していると判明したら、その対象の自動操作を停止。
- レシピがない/材料が食料として別用途に必要/栽培期が短い/食性が異なる/部分スキャンなら提案と根拠を出すだけで、確定的な作成や警告は行わない。
- 消費者が既存の400個体上限を超えた場合や計算上限に達した場合は、失敗状態を維持して自動操作しない。
- 大規模マップでは既存の10,000Tick更新と走査予算を尊重し、計画計算を毎Tick行わない。

## 検収シナリオ
- 飼料共有の2種・2放牧地、人間用食事との競合、冬季草成長0、腐敗、禁止された食料、未接続ゾーン。
- 既存の手動キブル指示とMOD管理の指示が共存しても、重複しない・手動を上書きしない。
- 不完全な予測では自動操作なし、目標達成後は停止、翌日の再評価でも増減振動なし。
- 手動設定変更・セーブ/ロード・途中削除・3MOD併用・270以上のMOD構成・TPS/計算時間と割当量を比較する。

## アプローチ
- A: 表示のみ—安全だが操作削減が小さい。
- **B: 共有予測を使った確認付き操作、機能別にAutoへ昇格（採用）**—根拠と操作を結ぶ。
- C: 全自動管理—競合と誤制御の危険が高い。
