# Animal Management 1.1.x レビュー是正・性能改善設計
> 2026-11-02 / review & planning only / implementation not started
> 基準 main `f382c94e11303ccb350681706eb29215616b0abc`
> 既存仕様 `docs/superpowers/specs/2026-11-02-actionable-automation-design.md`

## 意図と境界
レビューIssue #19–#26を、実際の自動操作の安全性→欠落ケース→使いやすさ→測定に基づく軽量化の順で是正する。既存3 MODのユーザーによる旧機能の正常プレイ確認を尊重する。**この追加機能の通常ゲームでの動作・TPSは未検証**であり #6 が担当する。新規機能の作り直し、他MOD・検証ホストの修正、ゲームDLLの公開、データの推測を行わない。Off/Confirm/Autoを保ち、Autoは必ず対象許可と根拠が必要。自動屠殺の追加許可・確認を変えない。

## 設計上の優先度と依存
1. **#25 安全性の最優先:** `ManagedFeedBills.Preview`の複数材料控除。現行の`ForecastSnapshot.Materials[Thing].Pool`は異なるThingDefを同じプールにまとめ得る。定義ごとの`debits[pool]`代入は上書きとなる。まず原材料の消費可能な全候補に対して「実際の栄養損失を過小評価しない」ことを示す。安全性を証明できない場合は該当Recipe/Autoを拒否。計算結果とバニラBillの実材料選択の差が残るなら安全なプレビューのみ。**UIより先に変更する。**
2. **#21 所有権の状態遷移:** `Bill_Production.repeatCount`等が作業完了で変化するか実物API/テストで確認したうえで、正常進捗・成功・期限切れ・ユーザー編集/停止・削除・権限撤回・セーブ/ロードを異なる遷移にする。正常な進捗と終了を「手動拒否」として永続`Revoked`に記録しない。手動介入後は引き続き安全側で自動管理を放棄する。同じ設備・許可で翌日再提案でき、二重Billを作らない。
3. **#19 備蓄ゼロの初期状態:** `Anchors`が空なら`FeedPlanningUI.Draw`が全機能を`return`する。既存Hay/Kibbleのスタックがなくても、適正飼育頭数を計算/表示できるようにし、飼料の計画はDef・食性・既知の到達性などで示せる範囲を区別する。「対象に実在するスタックへの経路」を証明できない状態で自動Billを作成しない。新規栽培区画を自動作成しない。
4. **#22 種別独立の上限:** 選択種だけ需要を変えているのに`AnimalDeficit`を全動物合計でゼロ要求すると、非対象種の既存不足のため可否が偽になる。選択種の不足と他種の**基準との差分**を分け、他種の不足を悪化させないことを条件に頭数を算出。共有備蓄を二重計上しない。対象種の需要が0の場合は推定不能/上限なし等を明示して誤った有限値にしない。
5. **#24 機能の独立:** `DrawCapacity`を`ProductionMode`に従属させない。予測/適正頭数の表示・設定と製造指示の書込み許可を分離する。既存設定との移行はConfirmを既定として安全側。スロットや自動屠殺の既存許可は無断昇格しない。
6. **#20 不確実性の細分化:** `WeatherDependent`を全予測の信頼性否定に兼用すると、草が存在する通常の放牧地でAutoが常に止まる。観測不完全/到達性不明/食性不明は絶対停止を維持。天候・季節の変動だけは保守的な複数シナリオ（例：放牧ゼロ、腐敗早期）で「いつでも安全で、同じ最小生産が有効」と証明できる場合に限り限定Auto。保証できなければ従来どおり停止し、停止理由を提示。将来成長を確定事実と表示しない。変更は#25/#21完成後。
7. **#26 動作監査UI:** `AnimalActionState.History`は最大20件あるが表示されない。プレビュー・許可・作成/停止/権限解除・Auto抑止理由をマップ別に確認できるUIを設け、時刻/対象/操作/結果の構造化表記と日英キーを揃える。同じ抑止理由を毎Tick追加せず、状態変化・明示操作のみ記録。ログの保存と削除が無限増加しないこと。
8. **#23 最適化:** `Calculate`内の`new string(access.Select(...).ToArray())`と`stock.IndexOf(pool)`、`FeedScenario.Plan`の多重max-flowが候補。先に正しさとメモリ/時間を測り、`Access`ビット集合または等価キー、プール番号の直接保持、計画キャッシュ/計算予算を限定導入する。スナップショットの意味・順序・PartialScan・禁止食料を変えない。計測で無視できる箇所は触らない。

## 共通不変条件
- すべての自動書込みは、実行直前に新しい完全なスナップショットで再確認。必要な原材料を消費した後も人間・動物の不足が基準より悪化しないことを証明。証明できない場合は書込みゼロ。
- 明示的に停止/編集/禁止されたプレイヤーBillを上書き・再開・削除しない。所有Billには明確な境界と保存識別子がある。
- マップ移動・Bill削除・対象スタックの消失・MOD途中導入/削除・セーブ復元時に参照を誤転用しない。
- 飼育頭数の提案と製造Bill操作は独立。屠殺設定は別許可と実行ごとの確認を維持する。
- RimWorld 1.7基準APIは `research/vanilla-1.7.4985/` を先に参照。未検証の自動化APIを仮定しない。
- 日本語/英語は同じ内容。UIのスナップショットは古くなれば再検証を要求する。

## 採用/不採用の代替案
- 安全対策A: 異なる材料の一部合算だけ直す → **不採用**。材料選択・複数Poolの重複控除が未解決。
- **安全対策B: 材料選択の安全境界を確立し、必要なら拒否して段階解除 → 採用**。誤ったAutoを許可しない。
- 不確実性A: 天候ありならAuto永続停止 → 現状の安全側だが機能が常用不能。
- **不確実性B: 保守的シナリオで証明したケースだけAuto許可 → 採用**。推測による緩和をしない。
- 性能A: プール計算の全全面書換え → **不採用**。既存の正常な需要配分を壊すリスクが大きい。
- **性能B: 現状測定→低リスクの局所最適化→等価性試験 → 採用**。
